# 10. One Request, End to End

*What does the whole of Part II look like as a single call stack, and where does
that stack unwind back to the event loop?*

Everything in Part II has been described one layer at a time: listeners and connections, the network filter chain, the HTTP codecs, the HTTP filter manager, routing, and connection pools. This chapter puts them in a line. We take one concrete request — a single HTTP/2 `GET` arriving on a TLS listener, proxied to an upstream cluster that speaks HTTP/1.1 — and walk the call stack in the order the code actually executes it. Nothing here is new; every hop is a pointer back into a chapter that explained it properly.

Two things are worth fixing in your head before we start. First, every hop below runs on the *same* worker thread. A worker is a thread running a libevent loop in [`WorkerImpl::threadRoutine`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/server/worker_impl.cc#L168) (see [Chapter 1](./01-process-model.md)), and once a connection is assigned to a worker it stays there for its lifetime — including its upstream connection. The path is close to lock-free, but not absolutely: the cross-worker `post()` in hop 2 briefly takes the target dispatcher's post lock, an `ExactConnectionBalancer` takes a mutex on every accept (see [Chapter 4](./04-accept-path.md)), and the access-log write in hop 29 takes [`write_lock_`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/access_log/access_log_manager_impl.cc#L214) to hand bytes to a dedicated [flush thread](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/access_log/access_log_manager_impl.cc#L229). Shared-nothing is the design intent and the overwhelmingly common case; treat it as a strong rule with named exceptions rather than an absolute.

Second, the stack does not run from socket to socket in one go. It unwinds back to the event loop at several points, and resumes later from a fresh libevent callback. Those points are marked **[loop]** below; they are the part readers most often get wrong.

One scope note. Every hop below traces HTTP over TCP: an `accept(2)` loop, a TLS transport socket, and a network filter chain terminating in the connection manager. A QUIC connection reaches roughly the same place by a different route (see [Chapter 4](./04-accept-path.md)) — datagrams reach a worker at [`ActiveQuicListener::onDataWorker`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/quic/active_quic_listener.cc#L172), which hands them to QUICHE's `QuicDispatcher` to be demultiplexed by connection id (the same id having already picked the worker — in the kernel where the [BPF socket option](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/quic/envoy_quic_connection_id_generator_factory.h#L40) is available, and otherwise in [`ActiveQuicListener::destination`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/quic/active_quic_listener.cc#L255), which redirects the packet to the right worker), and [`EnvoyQuicDispatcher::CreateQuicSession`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/quic/envoy_quic_dispatcher.cc#L95) runs the listener filters, does the filter chain match and calls `createNetworkFilterChain` itself. There is no transport socket on that path at all: the QUIC stack handles all L4 data, so the [QUIC transport socket factory](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/quic/quic_transport_socket_factory.h#L40) supplies a TLS context instead of a socket, and the handshake and stream framing live in the session. The connection manager does still build a codec, but for QUIC it does so in [`onNewConnection`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L584) rather than lazily on the first buffer, and that codec is a thin shim: QUIC connections bypass `onData` entirely, so its `dispatch()` panics if reached. From [`setUpRequestDecoder`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/quic/envoy_quic_server_session.cc#L153), which `CreateIncomingStream` runs for a new request stream and which calls the same `newStream` as hop 10, the two paths converge.

## Accepting the connection

1. The listen socket becomes readable. libevent invokes the callback registered when the listener was constructed, which lands in [`TcpListenerImpl::onSocketEvent`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/network/tcp_listener_impl.cc#L63). It loops calling `accept(2)` until the kernel is drained or a per-event cap is hit, wrapping each new fd in an `AcceptedSocketImpl`.

2. Each accepted socket is handed to [`ActiveTcpListener::onAccept`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/listener_manager/active_tcp_listener.cc#L80), which checks the per-listener connection limit and forwards to [`onAcceptWorker`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/listener_manager/active_tcp_listener.cc#L109). If a connection balancer picks a different worker, [`ActiveTcpListener::post`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/listener_manager/active_tcp_listener.cc#L168) moves the socket to that worker's dispatcher and this stack ends. **[loop]** — the remaining hops resume on the other worker thread.

3. Otherwise an `ActiveTcpSocket` is created and [`ActiveTcpSocket::continueFilterChain`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/listener_manager/active_tcp_socket.cc#L124) runs the listener filters. A filter that needs bytes off the wire — the TLS inspector's [`Filter::onAccept`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/extensions/filters/listener/tls_inspector/tls_inspector.cc#L111) is the canonical one — returns `StopIteration`, a `ListenerFilterBufferImpl` is installed, and the stack unwinds. **[loop]** — iteration resumes from the buffer's read callback once the ClientHello has been peeked.

4. When the last listener filter returns `Continue`, [`ActiveTcpSocket::newConnection`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/listener_manager/active_tcp_socket.cc#L196) calls into [`ActiveStreamListenerBase::newConnection`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/listener_manager/active_stream_listener_base.cc#L27). This is where the filter chain match happens (see [Chapter 4](./04-accept-path.md)): the SNI and transport protocol recorded by the listener filters select a `FilterChain`, its transport socket factory produces a `SslSocket`, a `ServerConnection` is built around the two, and `createNetworkFilterChain` instantiates the network filters — for us, a single terminal filter, the HTTP connection manager.

## The TLS handshake and the first HTTP/2 bytes

5. **[loop]** The connection's fd becomes readable and [`ConnectionImpl::onFileEvent`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/network/connection_impl.cc#L719) runs, dispatching to [`onReadReady`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/network/connection_impl.cc#L765), which calls `doRead` on the transport socket.

6. [`SslSocket::doRead`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/tls/ssl_socket.cc#L110) sees an incomplete handshake and drives `doHandshake()` — which bottoms out in `SSL_do_handshake` inside the handshaker — instead of reading application data, returning zero bytes. **[loop]** — several round trips of this happen before the handshake completes. When it does, [`SslSocket::onSuccess`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/tls/ssl_socket.cc#L193) records the handshake timestamp and raises `ConnectionEvent::Connected`.

7. On a later read event `doRead` decrypts into the connection's read buffer, and [`ConnectionImpl::onRead`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/network/connection_impl.cc#L447) pushes it through [`FilterManagerImpl::onContinueReading`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/network/filter_manager_impl.cc#L62), which calls `onData` on each read filter in turn.

8. The terminal read filter is the connection manager. [`ConnectionManagerImpl::onData`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L515) lazily builds the codec on the first buffer via [`createCodec`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L494) — ALPN already told the transport socket this is `h2` — and then calls `codec_->dispatch(data)`.

9. [`Http2::ServerConnectionImpl::dispatch`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http2/codec_impl.cc#L2539) feeds the bytes to the nghttp2/oghttp2 adapter, which parses frames and calls back. A HEADERS frame for a new stream id reaches [`ServerConnectionImpl::onBeginHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http2/codec_impl.cc#L2504), which creates a `ServerStreamImpl` and asks the callbacks for a request decoder.

10. That call lands in [`ConnectionManagerImpl::newStream`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L410), which allocates the `ActiveStream` — the per-request object that owns the stream info, the tracing span, the timers, and the HTTP filter manager.

11. When the header block ends, [`ConnectionImpl::onHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http2/codec_impl.cc#L1285) calls [`ConnectionImpl::ServerStreamImpl::decodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http2/codec_impl.cc#L710), which invokes `decodeHeaders` on the decoder from hop 10. We are still inside the original libevent read callback.

## Decoding: filters and routing

12. [`ActiveStream::decodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L1352) snapshots the route configuration, sanitises headers, creates the downstream filter chain, and calls [`traceRequest`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L1608) to start the ingress span. It then calls `filter_manager_.decodeHeaders`. If the connection has already processed its quota of requests this I/O cycle, [`shouldDeferRequestProxyingToNextIoCycle`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L2629) defers instead. **[loop]**

13. [`FilterManager::decodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/filter_manager.cc#L592) walks the decoder filters (see [Chapter 6](./06-http-connection-manager.md)). Any filter returning `StopIteration` unwinds the stack here; the request resumes only when that filter calls `continueDecoding()`, possibly from a completely different event.

14. The terminal decoder filter is the router. [`Router::Filter::decodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/router.cc#L477) resolves the cached route (see [Chapter 7](./07-routing.md)), resolves the cluster, and selects a host and connection pool (see [Chapter 8](./08-upstream.md)); [`Filter::continueDecodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/router.cc#L787) then builds an `UpstreamRequest` and calls `acceptHeadersFromRouter` on it.

15. [`UpstreamRequest::acceptHeadersFromRouter`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_request.cc#L412) calls `conn_pool_->newStream(this)` *before* running the upstream filter chain, so connection setup overlaps with filter work.

## Getting an upstream connection

16. [`HttpConnPoolImplBase::newStream`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_pool_base.cc#L60) delegates to [`ConnPoolImplBase::newStreamImpl`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/conn_pool/conn_pool_base.cc#L327). With a warm HTTP/1.1 connection available it attaches immediately; on a cold pool it queues a pending stream and calls [`tryCreateNewConnections`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/conn_pool/conn_pool_base.cc#L166), which opens a socket and returns. **[loop]** — the request is now parked with nothing on the stack.

17. When the upstream socket connects, its own `ConnectionImpl::onFileEvent` fires and the event propagates to [`ConnPoolImplBase::onConnectionEvent`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/conn_pool/conn_pool_base.cc#L563), which moves the client to `Ready` and calls [`onUpstreamReady`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/conn_pool/conn_pool_base.cc#L402).

18. [`attachStreamToClient`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/conn_pool/conn_pool_base.cc#L233) charges the circuit breakers and calls [`HttpConnPoolImplBase::onPoolReady`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_pool_base.cc#L84), which asks the HTTP/1 `ActiveClient` for a `RequestEncoder` and hands it to [`UpstreamRequest::onPoolReady`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_request.cc#L634). That records upstream addresses and timings and notifies the upstream filter chain.

19. The notification reaches [`UpstreamCodecFilter::onUpstreamConnectionEstablished`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_codec_filter.cc#L42), which replays the headers it latched earlier into [`UpstreamCodecFilter::decodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_codec_filter.cc#L54) — the terminal filter of the upstream chain, whose only job is to call `encodeHeaders` on the codec. That chain is built per `UpstreamRequest`, in [its constructor](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_request.cc#L99), so a retry attempt gets its own copy of it; the codec filter is the [only supported terminal filter](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_codec_filter.h#L29) for it. See [Chapter 8](./08-upstream.md).

20. [`Http1::RequestEncoderImpl::encodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http1/codec_impl.cc#L445) serialises the request line and headers and [`ConnectionImpl::flushOutput`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http1/codec_impl.cc#L349) calls `connection().write()`.

21. [`ConnectionImpl::write`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/network/connection_impl.cc#L590) runs the write filter chain, moves the bytes into `write_buffer_`, and calls `activateFileEvents(Write)`. No syscall happens here: [`FileEventImpl::activate`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/event/file_event_impl.cc#L35) schedules a callback for the *next* loop iteration. **[loop]** — the actual `writev` happens in [`ConnectionImpl::onWriteReady`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/network/connection_impl.cc#L866).

## The response

22. **[loop]** The upstream socket becomes readable. `onFileEvent` → `onReadReady` → raw-buffer `doRead` → `onRead` → the upstream connection's read filter chain, whose `CodecClient::CodecReadFilter` forwards to [`CodecClient::onData`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/codec_client.cc#L187).

23. [`Http1::ClientConnectionImpl::dispatch`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http1/codec_impl.cc#L632) parses the status line; [`ClientConnectionImpl::onHeadersCompleteBase`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http1/codec_impl.cc#L1521) calls `decodeHeaders` on the pending response decoder.

24. Through the pool's stream wrapper this reaches [`UpstreamCodecFilter::CodecBridge::decodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_codec_filter.cc#L149), which stamps the first-upstream-byte timing and runs the upstream encoder filter chain, ending at [`UpstreamRequest::decodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_request.cc#L295).

25. [`Router::Filter::onUpstreamHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/router.cc#L1843) applies route-level response header mutations, then calls `callbacks_->encodeHeaders`, i.e. [`ActiveStreamDecoderFilter::encodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/filter_manager.cc#L541). We have crossed from the upstream half of the request back into the downstream filter manager.

26. [`FilterManager::encodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/filter_manager.cc#L1314) walks the encoder filters in reverse order and finally calls [`ActiveStream::encodeHeaders`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L1906), which adds `date` and `server`, evaluates drain-close, and calls `response_encoder_->encodeHeaders`.

27. [`Http2::ConnectionImpl::StreamImpl::encodeHeadersBase`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http2/codec_impl.cc#L372) submits the header block to the adapter, which serialises frames through [`ConnectionImpl::onSend`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/http2/codec_impl.cc#L1515) into `connection_.write()` — hop 21 again, on the downstream connection. **[loop]** before the bytes reach the client's socket.

## Teardown and the access log

28. When the encoder chain has seen `end_stream`, [`FilterManager::maybeEndEncode`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/filter_manager.cc#L1631) calls back into `ActiveStream::endStream`, which calls [`ConnectionManagerImpl::doEndStream`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L269).

29. [`doDeferredStreamDestroy`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L331) cancels the stream's timers, calls [`completeRequest`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L1032) — which finalises the tracing span — and then [`ActiveStream::log`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/http/conn_manager_impl.cc#L1020), which is the access log line. Note it is emitted here, from a stack that began as an *upstream* socket read.

30. The `ActiveStream` itself is not freed inline. It is handed to [`DispatcherImpl::deferredDelete`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/event/dispatcher_impl.cc#L249), which schedules destruction for later in the same loop iteration so that no frame above it holds a dangling reference (see [Chapter 11](./11-event-loop-and-threading.md)). **[loop]**

## Watching it happen

The tools are [Chapter 13](./13-observability-and-operations.md)'s subject; what is worth
recording here is which hop each one shows you.

Trace logging is the most direct. Because `ENVOY_CONN_LOG` and `ENVOY_STREAM_LOG` prefix every line with the connection and stream ids, a `-l trace` run grepped for one such prefix reads as a transcript of exactly the hops above; the admin `/logging` endpoint takes a per-logger-id query, so `http2` or `pool` can be raised to trace without drowning in `conn_handler`.

The admin interface exposes the state each hop touched: `/clusters` shows the host chosen in hop 14 along with its circuit breaker and outlier state, `/stats` carries the counters incremented in hops 8, 16 and 18, and `/config_dump` shows the listener and route configuration that the snapshots in hops 4 and 12 were taken from.

Tracing gives the same picture with timing attached. The downstream span starts at hop 12 and is finalised at hop 29; a child span is created in the `UpstreamRequest` constructor ([`UpstreamRequest::UpstreamRequest`](https://github.com/envoyproxy/envoy/blob/981d3923fed302ab44ee9fd265fb078d4aabbd85/source/common/router/upstream_request.cc#L99)) and closed when the upstream response completes, so the gap between parent start and child start is the cost of hops 13-14, and the child's duration is hops 15-24. The finer-grained timestamps — handshake complete, first upstream tx byte, first upstream rx byte, last downstream tx byte — live on the stream info and are available to access log formatters (see [Chapter 9](./09-response-and-teardown.md)), which is usually the cheapest way to find out which of the **[loop]** boundaries above your latency is hiding behind.
